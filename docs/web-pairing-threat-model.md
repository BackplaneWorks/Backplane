# Browser pairing proposal for 0.16.4

Settings › Devices controls browser access. It starts off. When enabled, show the hub’s tailnet HTTPS address. Opening it displays a pairing page. The browser and the native Devices page display the same six digits. The person compares them and approves on the desktop or a paired phone. Devices lists the browser by name so the person can revoke it later.

## Trust and transport

Protect chats, files, viewer data, vault contents and device credentials from other tailnet members, hostile websites and stolen sessions. Trust the operating system, the hub, tailscaled and the approving native device. A compromised paired browser can act within its granted permissions until revocation. Revocation ends future access. A recipient can retain content already delivered.

Use an explicit tailnet-only HTTPS Serve mapping to a dedicated loopback browser listener. Verify the configured MagicDNS authority including its port. Keep this listener separate from native loopback trust and route registration. Refuse public Funnel exposure and fail closed when the ingress configuration cannot be verified. Local processes can connect to a loopback backend, so every protected operation still requires pairing. Bind the request and the approved device to the login verified by tailscaled. Require that login at redemption, on every authenticated GET or POST and at websocket upgrade. Return 401 for a missing or changed login. A client-supplied identity header on a loopback socket proves nothing. The listener must authenticate the proxy peer before accepting its identity assertion, or obtain identity directly from an authenticated Tailscale transport. Fail closed when neither is available. Cookies are shared across ports on a hostname. Settings must tell the person that other HTTPS services on this machine name receive the cookie. Use this shared hostname only with services they trust.

## Pair and authenticate

1. A same-origin POST to /auth/web/request creates a two-minute in-memory request and returns the comparison code. Issue an independent random polling secret in __Host-bp_web_pair with Path=/, HttpOnly, Secure, SameSite=Strict and Max-Age=120. Keep its digest server-side. Bound pending requests, body sizes, and request and poll rates per verified peer and hub-wide.
2. Deliver the pending name and comparison code only to authorized approvers through devices.page. Escape the untrusted name. Approval and denial consume the pending decision atomically. Restart, expiry and disabling browser access discard pending requests.
3. POST /auth/web/poll with the polling cookie redeems approval once. Persist the digest of a fresh credential and browser kind in devices-v1.json before sending Set-Cookie for __Host-bp_web with Secure, HttpOnly, SameSite=Strict and Path=/. Clear the pending cookie. Keep both credentials out of URLs, bodies, traces, client storage and frames.
4. In auth.rs, resolve the cookie to a live browser device for each protected HTTP request and websocket upgrade. Scope that credential to browser routes and approved data/1 commands. Enforce exact configured HTTPS Origin on POST and websocket upgrade, rejecting missing or ambiguous headers. Enforce the configured Host on every route. Allow browser RPCs by explicit operation and parameter scope in the dispatcher. Deny unknown operations, generic dispatch to disallowed actions, invitation minting, raw secrets, browser-access settings and ingress or peering mutations. POST /auth/web/logout revokes the current device and clears its cookie.
5. Enforce idle and absolute expiry server-side across restarts and on open sockets. Advance idle expiry on user-initiated commands. Heartbeats, automatic refreshes and server pushes leave the deadline unchanged. Revoke by device ID, invalidate pending writes and close all its sockets within one second. Disabling access terminates active sockets and blocks further browser requests immediately.

## Data and rendering

Serve only the pairing page, its necessary static resources and minimal health information before authentication. Use the phone wire projection for masked chat and viewer data. Pass /files/get, /bots/<thread>/screen.jpg and /message-image through the shared verifier and preserve their resource-specific path and snapshot checks. Send private, no-store on sensitive responses. Serve project HTML or SVG downloads as attachments or through an isolated origin. Keep uploaded content outside script and worker asset paths. Restrict script, style, worker and connection sources by CSP, forbid framing and object embeds, and set nosniff and no-referrer.

Implementation touches net/listener.rs for ingress, wire/mod.rs for HTTP and upgrade dispatch, auth.rs for the verifier, net/pairing.rs for registry durability, net/devicespage.rs for approvals and files/imgroutes.rs for image authorization. net/pairflow.rs provides the human approval pattern. net/owner.rs permits an absent Origin for native clients and issues broader cookies, so the browser boundary needs its own checks.

The release decision includes session lifetime and whether the person enables a dedicated Serve mapping or supplies one. Validate these controls with synthetic sessions on an isolated test hub behind loopback TLS and assert the production cookie names and attributes in headless Chromium before enabling the feature.
