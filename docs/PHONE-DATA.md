# Phone data protocol (data/1): plain data over one WebSocket, no presenter, no view schema

Agreed between the iOS lane and net (hub side), from the user's design ("we just send the data"). The Rust hub sends data; the SwiftUI app renders it
natively with typed Codable structs, cache-first. Fresh-home screens only: projects, threads, one thread (entries, composer, asks), Improvements.

## Transport
- Discovery: `GET /client/capabilities` (Bearer) gains `"data":{"proto":"data/1"}`; the app uses this protocol when it is present.
- Socket: `ws://host:port/ws?data=1&enc=json&token=<tok>` (hub token or a paired device's; revoke closes the socket). One socket per hub.
  `enc=json`: JSON text frames both ways (the app has no CBOR codec; default without `enc` is binary CBOR, plain string keys).
- First frame: `{"t":"hello","proto":"data/1","hub":"<host:port as asked>","name":"<the machine's name: BACKPLANE_NAME, else its host name; a phone's title>","version":"…","epoch":"…","now":<ms>}`; `{"t":"hb"}` every 15 s.
- Request `{"id":<u64>,"m":"…","p":{…}}`; reply `{"t":"reply","id","ok":true,"result":{…}}` or `{"t":"reply","id","ok":false,"error":"text"|{"code","message"}}`.
- Times: unix ms. Ids and cursors: opaque strings. `next:null` = no more.

## Types
```
Project = {id, title, root, origin, threadCount, updatedAt, waiting, icon, color, css, mark?, also?, marks?, newOn?}
          origin = the folder's git origin remote, normalized (`github.com/o/r`; "" for none): the key that makes one repository on two machines one project
Thread  = {id, project, title, state, updatedAt, pinned, pinOrder, settled, settledAt, archived, provider, model, preview, waiting, status?, parent, mark?}
          status? = the sidebar dot's word (feature `status`; signal.rs, children's work included): active, waiting, blocked, failed, stalled, finished (a turn done and not
          yet settled: the desktop's green dot, "ready for you to look at"), settled, inactive. `parent` is the thread it sits under (subagents, subthreads) as the
          desktop's sidebar nests it: a child goes with its parent, wherever that is.
          pinOrder = where a pinned thread stands on its project's Pinned shelf (0 first: the order the pins were made, or a drag's), so a phone lists pins as the desktop does; 0 when not pinned
          mark? = {name, short, away, label, runs}: the machine the thread runs on when it is another one (see One project across machines); absent for this hub's
          state ∈ "idle" | "working" | "asking" | "failed"; preview ≤ 140 chars; waiting = open asks
Entry   = {id, kind, text, at, clientId?, live?, agentOnly?, tool?, ask?, replyTo?}
          kind ∈ "user" | "assistant" | "tool" | "ask" | "note" | "step"
          replyTo: {id, quote} on the person's reply to a message (the desktop's Reply): `text` is what they wrote, `quote` the first line of the
          message answered. Draw "↩ In reply to: <quote>" (`gpui.b.in.reply.to`) over the bubble; a tap goes to `id` (read older pages until held).
          agentOnly: true on a message only the agent reads (the hub's note about a quote it posted): a client does not show it; in a bot's conversation (the uberbot's chat) also
          everything the hub hands the bot: launched-thread and task reports, watched work, mailroom/triage input, wake/routine/webhook
          prompts, other threads' messages, `[Backplane]` notes and system notes (`present::thread::bot_private`). A launched thread that
          waits on the person stays.
          live: true on the assistant entry still streaming (its text so far; later `k:"text"` pushes append to it)
          tool = {name, summary, state ∈ "running" | "done" | "failed"}
          ask  = {id, state ∈ "open" | "answered", question, options:[{id,label}], answered?:<option id or text>}
```
## Reads
`projects.list {limit?=50, before?}` → `{projects, next}` (recent first) · `threads.list {project?, limit?=50, before?, archived?=false, settled?}` → `{threads, next}` ·
`thread.entries {thread, limit?=40, before?}` → `{thread, entries (oldest→newest within the page; newest page first), next}`; the streaming entry (live:true) is included.
`dirs.list {path?}` → `{path, parent, dirs:[name]}` (browse the hub's folders to choose a project; default = home) — for `project.add`.
## Writes
`project.add {path, title?}` → `{project}` · `thread.create {project, title?, text?, provider?, model?, effort?, runtime?, permission?:"ask"|"auto"}` → `{thread}` (with `text` also sends it; default
permission "ask" so approvals appear) · `message.send {thread, text, clientId?}` → `{entry}` (same clientId twice posts once) · `ask.answer {ask, answer}` → `{}` (answer = an option id,
or free text for a question) · `turn.interrupt {thread}` → `{}`.
## Subscriptions
`subscribe {topic:"lists"}` / `{topic:"thread", thread, sinceEntry?}` → `{sub}` · `unsubscribe {sub}`. Pushes `{"t":"d","sub","k",…}`: `thread` {thread} (upsert) · `thread.removed` {id} ·
`project` {project} · `entry` {thread, entry} (appended or whole-replaced by id; a user entry carries the sender's clientId) · `text` {thread, entry:<id>, append, at} · `turn` {thread, state}.
On reconnect the app resubscribes and re-reads lists and the open thread (no resume).

## Star suggestion (feature `star`; `native/host/src/state/star.rs`)
- After a person's fifth prompt, or a prompt three days after their first with at least two counted (counted once per hub home: `turn.start`, `bots.say`, `bots.post` from a client, never a retry, blank text or agent mail) the hub offers a GitHub star.
- `star.offer` → `{offer}`: `null`, or `{token, text, url, label, repo, why}` while the offer is out and undecided. Ask it on every (re)connect.
- Frame `{"t":"star","offer":…}`: to the prompting socket when the offer is made (or when a snoozed one is out again, at the next prompt), and `offer:null` to every socket once it is decided (hide the card).
- `star.nudge {token, action: open|dismiss|later}` → `{}`. `open` (Star on GitHub, which also opens `url`) and `dismiss` (Don't ask again) are final; `later` hides it for a week, then `star.offer` answers it again under the same token.
- Shown as a small card that blocks nothing (the desktop: the window's upper right corner; the phones: under the top bar): `text` as its title, `repo`, `why`, a Star on GitHub button, then Later and Don't ask again. It waits (`star::due` on the desktop, the same rule on the phones) while the thread on screen runs a turn, while the composer has text, and during setup, so it comes after a turn has ended.

## Telemetry notice (feature `telemetryNotice`)
- A one-time strip saying what anonymous usage the hub sends, with Turn off, Settings and a close ✕. Only when the hello's `features` has `telemetryNotice`.
- `telemetry.notice` → `{notice}`: `null`, or `{token, text, off, settings}` (all strings): `text` the notice's words, `off` the turn-off button's label, `settings` the settings link's label. Ask it on every (re)connect. A notice with an empty `token` or `text` is none.
- Frame `{"t":"telemetry.notice","notice":…}`: to every socket whenever it changes; `null` hides the strip.
- `telemetry.notice.act {token, action: shown|close|off}` → `{}`. `shown`: once per token per app session, when the strip is actually drawn on screen (not on receipt in the background); it is what lets the hub start sending. `close` (✕) and `off` (turns all telemetry off on the hub) hide the strip at once.
- Settings opens the app's own Settings (its privacy setting where it has one); it sends nothing and leaves the strip. The strip sits where the star strip goes, above it when both show. Hub words go through the English-text lookup, as the star's.

## Viewers, files, browser (2026-11-06; features `viewers`, `files`, `browser`; `native/host/src/data/ext.rs`)
Each is the hub's own request (kicad.watch, files.dir, mech.list, bots.browser, kicad.info), run for the folder of the thread. `viewer.watch` makes plots arrive on this socket, so a phone subscribes to a source the way the desktop does.
- `viewer.files {thread}` → `{root, pro, pcb, sch}`: the project's canonical KiCad files.
- `viewer.watch {thread, kind: board|schematic|3d|3d-bare|3d-full|split|"" (stop), path?, tree?, kept?}` → `{root}`. `kept`: the 3D model the phone has cached for this view, as `<key>\t<id>` (its plot key and FNV-1a 64 of its `mesh` bytes, 16 hex digits, `plot::mesh_id`; an older phone sends the id alone); the hub skips sending that model for that key only. Each watch starts afresh: whatever the hub sent this phone for its last view is not taken as held, so the new view's model and parts come again (only the model `kept` names is skipped). The reply's `keys` are the plots this view shows: a phone shows only plots with those keys and drops what comes late for the view it left (an older hub sends no `keys`: the phone derives them from `root` by the hub's `kind|root|path` rule). A `{t:"plot", key, none}` comes as JSON on the data socket (why a view has nothing to show). Then, until another watch or a close: a **binary** CBOR frame per change, the hub's own (`kicad/plot.rs`): a plot `{t:"plot", key, fam, base, box, edge, thick, cs:[index of a chunk the phone holds | {s,l,c,a,m,w,d}]}` (the delta against what this connection holds; chunks are varint paths in micrometres, `m` 0 fill / 1 stroke / 2 dot), a model `{t:"plot", key, box3, n, mesh}` (triangles as zigzag-delta varints, 10 µm), or `{t:"plot", key, none:"why"}`. Keys: `0|root|path` board, `1|…` schematic, `2|…` 3D model (`3|` bare), the board's plot rides under its model. A path is from the project's root (a STEP for Mech: kind `3d`).
- Parts of a board's 3D model (`2|…`) stream after the bare board when the hub makes the model itself (`kicad/pcb3d`, the default; setting `viewer.board3d` = `kicad-cli` turns it off, and then the model has its parts in it as before). Two more binary frames, under the model's key:
  - `{t:"plot", key, parts:{of, rev}}` starts the parts again: drop every part held for `key`. `of` instances will come (0: none); `rev` is the board file's revision they are of. It always follows a board `mesh` or, when the phone's `kept` model was the board, the watch.
  - `{t:"plot", key, part, n, mesh, at, refs, done}`: one model and every instance of it. `part` is the model's id (16 hex digits); `n` and `mesh` are its triangles in the model's own frame, encoded as a board's `mesh` (10 µm integers, board axes); `at` is a byte string of 48 bytes an instance: 12 little-endian f32, a row-major 3×4 affine that takes the mesh's integer coordinates to the board model's (`x' = a0·x + a1·y + a2·z + a3`, then the next row for y', z'); `refs` the instances' references, in order; `done` how many instances have now been sent (the progress is `done`/`of`). A part whose model is missing or would not convert comes the same way, as a box over its courtyard (an id starting `b`).
  - Each instance fades in, opacity 0 to 1 over 300 ms from its arrival (redraw only while one is fading). A tap still picks from the board's plot, so refs work before a model arrives.
- `viewer.info {key, at, idx}` → `{info}`: what the piece is (`kind;net=…;layer=…;width=…`), `at` the chunk's place in the plot held, `idx` the piece's info index; `viewer.probe {key, name, value}` → `{matches:[[at, idx]]}` (net or part highlighting).
- `files.entries {thread, path?}` → `{dir, entries:[{dir, size, name}]}`; `mech.list {thread}` → `{parts:[path], renders:[path], primary}`; bytes of a file: `GET /files/get?thread=&path=&token=` (a path outside the project is 400).
- `browser {thread, op, …}` → `{}`: `takeover`, `handback`, then `click {x, y}` (0..1000 of the page), `type {text}`, `press {key}`, `scroll {dx, dy}`, `navigate {url}`, `toolbar {command: back|forward|reload}` (takes the page over, then goes on the page's input queue like a tap, so it answers at once; another command is refused); without the takeover the input is refused ("take over the browser first"). The input runs on the page in the order it was sent; `press` keys are the page's names (`Enter`, `Backspace`, `Tab`, `ArrowLeft`/`Up`/`Right`/`Down`), `scroll` is in page pixels. The page's newest frame is `GET /bots/<thread>/screen.jpg?token=` (404 until the helper writes one), a new one announced as `{"t":"shot","bot":<thread>,"n":N}` (JSON, text frame).

## Diff and Review (features `diff`, `review`; `native/host/src/data/ext.rs`)
- `viewer.diff {thread, from?, to?}` → `{diff, nogit?}`: the hub's `git.diff` as unified text, by default the thread's checkpoint (made when its first turn started) against the work tree now; `nogit` names the folder when it is not a repository.

## The Hub screen (`HubRescue.kt`/`.swift`, `HubScreen.kt`, `HubView.swift`)
Restarting the hub must work when its views are broken, the socket is down, or only its guard answers, so this is native UI on plain HTTP to the paired address, and nothing here goes through the socket. The app reaches it from Settings and from the offline banner.
- `GET /healthz`, no credential: 200 `{status: ok|degraded, safe, …}`, 503 `{status: starting|hung|down, …}`; `status:"down"` with `rescue:1` is the guard answering on the hub's address. Every one of these bodies is an answer, a 503 as much as a 200.
- `GET /hub/status`, `Authorization: Bearer <token>`: `{guard:{state, mode, build, text, actions:[{id, label, text?, remote?}]}, incidents:[{at, what, why, did}], hub:{…}, notice:{text, tone, actions}}`. In rescue the same with `rescue:1` and no `hub` or `notice`. `guard:null`: this hub has no guard. Incidents come oldest first and `at` is in unix **seconds**, unlike the rest of this file. `remote:false` on a rollback says the hub will refuse it from a phone; the app draws it anyway and shows the refusal.
- `POST /hub/control {action: restart|normal|safe|rollback}`, the same credential: 202 `{ok:true, text}`; 409 `{ok:false, text}` is a refusal to show as it stands (3 restarts in 5 minutes, a rollback that would lock the person out, no guard); 401 the credential was refused. Another status with a `text` (503 "the guard did not answer") is shown as well.
- The buttons are `guard.actions`, one each; the app adds none of its own unless `/hub/status` cannot be fetched or `guard` is null, when it offers a built-in `restart`. With no guard the hub's reason is control's 409, so the app sends that only on a confirmed tap, never by itself. Each action is confirmed first, with its `text` when it has one.
- After a 202: `/healthz` every 2 s for up to 3 minutes until `ok`, `degraded` or `down`, stopping when the screen goes away and pausing while the app is in the background. The old hub (or rescue) goes on answering for a moment after its 202, so such an answer counts only once the restart has shown (no answer, `starting`, `hung`) or 10 s have passed. A request to `/healthz` gives up after 5 s, the others after 12 s; the credential is not sent on through a redirect.
- A 0.14 home coming across (`docs/IMPORT-0.14.md`): `hello.migrating` is null, or the import's state with its `card`; while it runs the hub pushes `{t:"migrating", state:"running", phase, what, done, total, pct, eta_s, projects:[n,N], threads:[n,N], current, card}` about once a second, then once `{t:"migrating", state:"done"|"failed", …, card}`. `card` is what to draw, words and all: `{state, title, body, pct (0-100, null on a failure), lines:[text], buttons:[{label, action, value, on}]}`. A banner over the lists and the thread shows title, the bar and the first two lines; tapping it opens the card. Its buttons run as `onboard.act {action, value}` (Continue writes `import.v014.ack`; Retry runs the import again). While `state` is running there is no dismiss. One push notice (`PushSent`, kind `import`) says it finished, for a phone that was away.
- `hello` carries `notice:{text, tone, actions}` (`text` empty when all is well, `tone` `warn` or `info`): a thin banner on the lists and the thread opens the Hub screen. `/hub/status` updates it too. The RPCs `hub.status` and `hub.control {action}` exist; the apps do not use them, since they need the socket.
- `test/mobile/hub_cases.json` holds both apps to the same decisions (`HubRescueTest`, `scripts/mobile/hub-check.sh`); `test/mobile/hub_stub.py` plays these routes.

- Feature `settled`: `settled` is the desktop's Settled shelf (a settle by the clock, by hand or by a merge; an unsettle or a new message takes a thread off it) and `settledAt` is when, in ms (0 off the shelf). `Project.settledCount` counts a project's settled threads that are not archived. `threads.list {settled: true}` lists only those, newest settle first (its cursor is `<settledAt>:<id>`); `{settled: false}` lists only the rest, newest activity first, so settled threads never push live ones off a page. ## The composer's commands (feature `commands`; `native/host/src/data/ext.rs`, `session/composer.rs`)
`/btw`, `/give`, `/secret` and `/intent` are never messages: `message.send` refuses them ("This app is too old ... Nothing was sent."), so an old app posts nothing.
- `hello.commands` → `[{word, label, desc}]`: the words, and the Send button's label while the draft is one (`/btw` Ask, `/give` Give, `/secret` Send, `/intent` Save). A draft is a command when it starts with the word alone or the word and a space or a new line.
- `composer.run {thread, text}` → `{kind, …}`: `btw {q}` (the answer comes as a push `{t:"d", k:"btw", thread, q, a}` to this socket only; the app shows the question and the answer in a card above the composer, closed by hand), `give` (the work was handed over: see Handoffs below), `secret {name}` (the app opens its masked box; `secret.set {name, value, purpose, thread}` saves, and the value is never a draft), `intent` (saved), `edit {text}` (`/intent` alone: the composer takes the project's intent to change). A refusal is the error, in plain words: the app keeps the draft and shows them.
- `secret.asks {thread}` → `{asks:[{name, purpose}]}`: an agent's open requests for a secret; a `{k:"secret", thread}` push says they changed; `secret.dismiss {name}`.

### Handoffs (`/give`; `native/host/src/commands/give.rs`, `commands/handoff.rs`)
`/give >thread %project @bot [note]` (also `bots.give {thread, text}`; the popup's words name the targets, the rest is the note) hands the thread's work over:
- The hub makes a **summary** of the conversation with the Writing setting's model (`text.write`; when none can be run, the thread's own last request and reply) and the **references** the work touched, newest first: `{kind, label, url, thread, path?, msg?, role?}` with `kind` `thread` (the source), `message` (`Asked:` the newest request, `Answered:` the newest reply; `msg` is its id), `board` (a KiCad file) and `file` (at most eight of those, the files its edit tools wrote; `path` is relative to the thread's folder, `url` the same). `thread` is the source thread: a phone opens a reference by `link.resolve {url, thread}` (a `backplane://thread/<id>#<msg>` url answers `{kind:"thread", thread, msg}`; a path answers `{kind:"file", thread, path}`).
- A **thread** target gets it as a message from the source (`MessageFrom {kind:"thread"}`): a running turn is steered at once, an idle thread starts one; it is never held behind a turn. A **project** target gets a new thread that way. A **bot** is woken with it (`bots.say`). With no agents module (a test hub) the text waits in the thread ahead of its next message.
- The receiving thread's log gets the **card** (an activity of tone and kind `handoff`, its text the card's JSON, kept whole); the source's log gets `Given to "<thread>"` (kind `fork`). The message itself is marked `agentOnly` (the agent reads it; draw the card).
- In `thread.entries` and its pushes the card is an Entry `{id, kind:"handoff", text: summary, handoff:{from, title, note, summary, refs}, at}`. Draw the summary, the note when there is one, a row for each reference that opens it (`link.resolve`), and "From <title>" opening `from`.
- `mentions.list` items carry the thread's, project's or bot's summary as `detail` when the hub has written one (0.14's menu showed it); the desktop's popup says the same. Summaries (`summary.<id>` settings, written when a turn ends) are kept and served this way; 0.14's `summary.set` and `thread.note` were only the hub's own job replies, never a client's request, so they stay unknown methods.

## Improvements: where a request goes (`native/host/src/settings/improvements.rs`)

- `improvements.projects {q}` → `{project, projects:[{id, title, root, machine, short}]}`: the projects of this hub and of the shown linked machines (a linked one's id is `<link>~<id>`, `short` its machine), every word of `q` in the title, folder or machine name, the last choice first, then this machine's, then each linked machine's, by title (at most 40). `project` is the last choice while it still exists, else "".
- `improvements.project {project}` remembers a choice (setting `improvements.project`); a project on no machine is refused. The apps then send with `thread.create {project, text}` as before: a linked machine's project makes its thread there.

## Conversation history (feature `history`; `native/host/src/data/ext.rs`, `sidebar.rs` `scratch_chats`)
The old Scratch chats: 0.14 stopped new ones and kept these. They open read and write as they were; nothing starts there. The desktop's sidebar group is the same list.
- The Scratch project is no project of `projects.list`, `search` or `mentions.list`, and its chats are not in `threads.list`. `thread.create {project:"scratch"}` is refused ("Conversation history takes no new chats. Start one in a project.").
- A `Thread` carries `history: true` when it is one of these chats (in `history.list`, `search`, `thread.entries` and pushes).
- `history.list {q?, limit?=50, before?}` → `{live, threads, next, count}`: `live` are the chats that want attention (an open ask, a running turn, still on the Pinned or Active shelf); a phone always shows them under the group's row. `threads` are the rest, newest first, paged like `threads.list`, shown while the group is open. `q` keeps the chats whose title has every word of it, any case. `count` counts every chat, the search aside; the group's row ("Conversation history (N)") shows only when it is above 0, and opens or shuts the list.
- `search` finds these chats by title: a phone shows them under a "Conversation history" heading. A `lists` push of a `thread` with `history: true` means the group changed: ask `history.list` again.

## Terminals (feature `terms`; `native/host/src/data/term.rs`, `term/stream.rs`)
The hub's own terminals: the chat terminals a thread opens (an agent's `terminal_open`), the threads' floating shells, and shells a phone opens itself. The screen is the hub's emulator's; a phone runs the same VT rules on the bytes (or draws the snapshot). A data/1 socket holds the hub's token or a paired device's (full access), so it types into them as the desktop does.
- Entry `{id, kind:"term", text:<title>, at, term:{key, id, title, cols, rows, cmd}}`: a chat terminal in a thread's entries (paging and `entry` pushes alike). Draw it as a card a few rows tall; its screen comes from `term.read`/`term.watch` under `key`. A thread's card stays after the terminal ends: its last screen is on the hub's disk, so it reads back after a restart (a terminal that was running when the hub stopped reads back `stopped`).
- A terminal's stream: each run of it has a name `g` (a new process, a restart, or a screen read back from disk is a new run) and counts the bytes it printed, `o`. The hub keeps the newest 128 KB of them.
- `term.read {key, g?, from?}` → `{key, g, o, state, running, cols, rows, title, b, from?, reset?}`. `b` is base64. With `from` (the offset the phone holds of run `g`) and the bytes still kept: `from` is echoed and `b` is what came after (feed it to the screen; the phone now holds `o`). Otherwise `reset:[cols, rows]` and `b` draws the screen on a blank terminal of that size: start a new screen, feed it, hold `o` of run `g`.
- `term.watch {key, g?, from?}` → the same, and from then on pushes on this socket (at most 16 watched at once): `{t:"d", k:"term", key, b, g?, o?, reset?, state?}`. A push with `reset` is a snapshot at `o` (a resize, or the phone fell behind): replace the screen, hold `o`. A push with `state` and no bytes is the terminal's state: `running`, `done N` (the command ended with N; its shell is still open), `exited N` (the terminal ended), `stopped` (hung up), `failed to start`. A push of bytes: with `held` what the phone holds, take it by `stream::merge(held, o, len)` (pure, with tests): `o > held` is a gap (send `term.read {key, g, from: held}`), all of it below `held` is skipped, else feed it from index `held - o` and hold `o + len`. A push of another `g`, or with no `g`, means read again. `term.unwatch {key}` → `{}`. Watch only while the terminal is on screen; otherwise show the last screen held. On a reconnect: `term.watch` again with the `g` and `from` held, so nothing printed while away is lost.
- `term.write {key, b? | text?}` → `{sent}`: bytes (base64 `b`) or text to the program, at most 256 KB; the keys' bytes are the emulator's (`Vt.key`: Esc is `\x1b`, Tab `\t`, arrows `\x1b[A..D` or `\x1bOA..D` in application cursor mode, Ctrl+letter its control code). A paste goes as bracketed paste when the screen asked for it (`\x1b[200~ … \x1b[201~`).
- `term.resize {key, cols, rows}` → `{}`: the pty's size; every client then gets a snapshot at the new size. Send it when the full-screen view's grid changes (rotation, font size), not for the card.
- `term.stop {key}` → `{}`: hang it up (a `stopped` state push follows).
- `term.list {project?, thread?}` → `{terms:[{key, kind: chat|shell|panel, thread, title, state, running, cols, rows, g, o, cwd, at}]}`: what the hub holds now, newest first. `term.new {project? | thread?, cols, rows}` → what `term.read` answers for the new shell (`key` `s:<project>:<n>`, `s::<n>` for the hub's home folder): a login shell in the thread's folder, the project's, or the home folder. The Terminals list of a project shows `term.list {project}` and offers New shell.

## Links in messages (feature `links`; `native/host/src/data/link.rs`)
- `link.resolve {url, thread?}` → `{kind:"thread", thread}` | `{kind:"project", project}` | `{kind:"room", room}` | `{kind:"file", thread, path, line}` | `{kind:"none", note}`. A file of another project (an absolute path, a `file://` address) answers that project's thread (the one given when it is that project's, else its newest); the app opens a board, schematic or model in its tab. `url` is a `backplane://` link (`thread/<id>` or `<machine>~<id>`, `project/<id>`, `conv/room%3A…`, `room/`, `bot/`), a bare id, or a path (`src/x.rs:12`, `src/x.rs#L12`, an absolute path under the thread's project folder). A file resolves only when it is a file inside that project (never through `..`); `path` is then from the project's root and `line` 0 when none was given. `note` is the short line the app shows when nothing opens. The phone picks what looks like a link in the text (web addresses, `backplane://`, emails, phone numbers, paths) and asks only for `backplane://` and paths when tapped.
- `thread.entries` of a `<machine>~<id>` thread this hub mirrors answers from the mirror (the thread object is bare: no project, no asks, no live text); `link.resolve` says `thread` for it only when the mirror holds it.

## The sidebar's sections (feature `sections`, docs/ALWAYS-ON.md section 8)

- `sidebar.sections {open?:[toggle], query?, page?:key, pageDone?, jump?}` → `{sections, groupsTo, page?, jump?}`: the same sections the window draws (present/sections.rs).
  A section is `{id, kind: "threads"|"projects", title, count, fold, open, toggle, group?, rename?, rows}`, in order: `needs` (Needs you, absent when empty), `pinned`,
  `active`, `group:<gid>` (folded until its `toggle` is in `open`), `quiet`. A thread row: `{id, title, word, say, want, ago, machine, mark, project, projectKey, off, nav}`
  (`word`: needs, running, limit, monitoring, failed, cut, interrupted, done, idle; `off`: its machine is off, known from the registry, and `nav` is ""). A project row:
  `projects.list`'s merged fields (`key`, `name`, `machines`...) with `running`, `needsCount`, `pinned`, `dots` and its visible `threads`. `page` is the project's page:
  `{key, project, sections: running, needs, recent, done ("Done (n)", folded unless pageDone)}`. `jump` lists every project and thread on every machine (Ctrl+K).
- `sidebar.act {action, value}`: `project-pin` key (toggles), `project-fold` key (toggles a project row's fold: its `folded` row has no `threads`/`swarms`, `under` counts what it hides), `group-rename` "gid\u001fname" ("" gives the automatic name back), `group-move` "key\u001fgid" (or "key\u001f+New name").
- Visibility (D11): a thread is listed while it runs, owns running work, asks the person, or stopped abnormally and was not opened or settled since; pinned ones always.
  A thread that asks the person is never hidden. The rest are on the project's page and in `jump`.
