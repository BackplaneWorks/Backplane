# Named Claude and Codex accounts

Backplane keeps named, machine-local subscription profiles, managed in the desktop client under Settings → Agents → Accounts. It does not import existing credentials or change existing default CLI homes. The phone apps have no account picker; the timeline lines below reach them from the hub.

The [pinned upstream research](research/multiple-provider-accounts.md) compares T3 Code commit `9e09926d97824179d97311d1a810c6b5bb60d2d1`, official Codex source commit `78a3185ecba7ca3422f14589aeac97059649f60f`, and Backplane's existing allowance work. T3 has several account mechanisms; this implementation uses independent CLI profiles and Backplane's conversation handoff, rather than shared native-session overlays or managed subscription tokens.

## Login and selection

Open Settings → Agents → Accounts on this machine. Add a Claude or Codex profile with a label, then choose Connect / Login. The label alone never establishes an authenticated account.

Codex uses the provider's app-server device ceremony. Backplane displays the provider URL and device code, tracks its own login ID, and accepts completion only from that profile's active app-server attempt. Claude uses its own `auth login --claudeai` ceremony. Backplane displays its authorization URL and provides a sealed input if the CLI asks for a sign-in response. That input goes directly to the matching attempt's stdin; it is not conversation text, a draft, command-line argument or persistent form value. Cancel, expiry and reconnect preserve any previously verified active store until a replacement verifies successfully.

Status / Refresh verifies the provider identity and retrieves supported metadata. The provider owns token refresh. Disconnect runs the supported provider logout and removes that profile's active private store. Login/disconnect refuse while an owned provider child still uses that profile. Failed verification never creates a successful account from CLI availability or a display name.

Delete account in Settings → Agents removes a saved profile and its local sign-in data after confirmation. Cancel a pending sign-in or finish its active turns first. Deleting a new-thread default clears that choice; existing threads keep their binding and require another account to be selected explicitly. The existing Default CLI accounts are left intact.

Use the Account chip beside the model to select between turns. Selection saves the old native session under its profile/generation, restores only the selected account's session, and hands over unseen recent conversation with an earlier-history pointer, which goes with the thread's next message. An active turn must finish or be stopped before a manual selection.

## When an account runs out

A usage limit or a failed login in a running turn (a provider's own error envelope, a rejected `rate_limit_event`, or what the process left on stderr when it ended with no result; never ordinary text) moves the thread to another connected account of the same provider and starts the turn again. This holds for an explicitly selected account too: the person's pick stays the thread's pin and is where it returns.

The planner (`settings/fallback.rs`) picks the eligible account with the most fresh provider-reported allowance; a fresh zero-remaining account is skipped, missing or stale readings come after known ones, and saved order breaks ties. The driver (`settings/driver.rs`) writes a hold on the login, keyed by profile and sign-in generation, and goes through the same step as a person's pick (`accounts.choose`), so each account keeps its own native session. A session lives in one account's store and the CLI cannot resume it under another login: an account that worked on the thread before resumes its own session and is handed what it has not seen; a fresh one is handed the conversation (`hand_text`, newest entries within its budget, with `thread_read` for the rest), then the continue note with the original request. What streamed of the cut-off reply is posted first, so it is part of what is handed over. Messages the person queued stay queued.

The timeline says one line: `Switched to Personal: Work ran out (resets 15:40)`, or `(reset unknown)`, or `Switched to Personal: Work could not sign in`. A turn that goes on is never marked failed, and its task and launcher are not told it ended (`TurnChanged` carries `failover: true`).

A request never returns to an account it ran out on (`account.failover.tried.<thread>`, cleared by the next request or a reset); this is what stops two accounts trading a turn. With no account left, the opt-in fallback hierarchy of Settings → Agents is tried, passing over a target whose own accounts are all held and never wrapping; such a switch hands the conversation to the new provider. Otherwise the thread says `Every claude account is out (Work, Personal). Continuing at 15:40, when the first one resets.` and goes on at the earliest reset, on the account that reset, wherever it stood. With no reset known anywhere it says so and waits for the person: no time is invented.

## An expired sign-in

A login whose OAuth session died (Claude Code: "Failed to authenticate: OAuth session expired and could not be refreshed", "OAuth refresh token is no longer valid; run /login", "API Error: 401"; a refresh-lock timeout is not one) is marked `expired` on the account (`accounts_io.rs` `after`, `expire`; kept in the registry as `expiredAt`, so a restart still knows). `claude auth status` only reads the credentials file, which still names the account after the session died, so it never makes an expired account connected again: only a sign-in, or a status check whose usage read the provider answered, does. A usage read the provider refuses in those words marks a connected account expired before any turn finds out. A turn cannot start on an expired account; it fails over as a failed login does. With no other account to take over, the thread waits ("Work's sign-in expired and no other claude account can take over. Continuing once you sign in again.", `provider.resume.<thread>` with `signin`), the hub records one alert a provider (`account.signin.alert.<provider>`), and the push module sends it in the uberbot's name: "Claude sign-in expired: tap to sign in again", with `link: "account:<id>"`, which opens that account's sign-in on a phone. Once the account is connected again, every thread its expiry stopped goes on, on the new sign-in, with the conversation handed over (`driver.rs` `signed_in`), and the alert leaves every phone.

Concurrent refreshes: Claude Code 2.1.319 takes a lock file in the profile's own store for each OAuth refresh and reads the token again under it, so the hub's children of one profile (turns, status and usage reads) never refresh one token twice. The hub does not refresh tokens itself (no credential leaves the CLI's store); it only keeps `CLAUDE_SECURESTORAGE_CONFIG_DIR` from leaking into a profile's children, which would share one store and one lock across profiles.

Phones: Settings, Accounts (data/1 feature `accounts`, docs/PHONE-DATA.md) lists the accounts per provider with their state and limits and offers Sign in again, Add account, Check now and Remove. The sign-in runs on the hub: the phone opens the provider's page in its browser and, for Claude, sends back the code that page shows; Codex shows its device code. No password is typed in the app.

A limit's reset comes from the provider's field, the time after a bar in Claude Code's words, a `rate_limit_event` seen earlier in the turn, or the fullest window of the account's own allowance. A hold with a known reset ends by itself. One with none ends when a reading newer than it shows allowance left, or for a failed login when a check after it proves the sign-in works (the provider answered a request made with it), or when the person picks that account. Once the account a thread left has reset, the thread goes back to it between turns with its own session and a note (`account.failover.preference.<thread>`). An explicit account, provider, model or mode choice replaces that. Defaults for new threads are unchanged.

## Choosing an account

The Account chip opens with Ctrl+Shift+A (⌘⇧A; rebindable in Settings). The menu has the keyboard: `1`…`9` pick the rows, Esc shuts it. Each row shows what the account has left, or `out, resets 15:40` from the hub, and the current one is ticked.

Agents and bots choose with the `account` argument of `thread_launch`, `delegate_task` and `thread_update`, by id, email or label (`default` is the CLI's own login), and read `account_list` for each account's remaining allowance. An account decides the provider when none is given; a name that fits two accounts is refused. A new thread with no account named freezes the provider's default, as one the person makes does.

`account.chosen.<thread>.<provider>` keeps who chose (`{id, epoch, by, who, at}`, `by` being `person`, `agent` or `bot`), and the timeline says it: `Bub selected Personal; ...`. What the person chose is the thread's pin. A bot or agent cannot move a pinned thread unless the person's own latest message, in that thread or in the one asking, names the account: the hub checks the log for that, and what any thread or bot sends carries a `MessageFrom` that says it is not the person. `accounts.choose` and `fallback.switch` are the hub's own requests and no connection may send them. A failover does not change who chose.

The menu lists saved Claude and Codex accounts together. Selecting an account from another agent switches the thread's agent and account in one guarded change. Settings also offers Use in this thread. Opening the menu after a restart rechecks saved sign-ins without a model prompt; unchecked accounts show checking feedback, and disconnected accounts show where to refresh or sign in. Missing accounts and old sign-in generations cannot silently use another account.

Each provider's new-thread default is frozen when a thread is created with that provider. Changing a default leaves existing threads alone. An old thread with no account binding continues to use its existing default CLI authentication and native session. Forks copy account bindings but receive their own thread/session ownership. Switching providers retains each provider's selected profile and catalog separately.

## Ownership and storage

| Item | Owner / representation |
| --- | --- |
| Public profile metadata | Machine, opaque profile UUID, provider, label, verified identity generation, safe identity/catalog/quota metadata |
| Thread binding | `account.thread.<thread>.<provider>` → `{id, epoch}`; missing old binding means legacy default |
| Native session and handoff cursor | Length-prefixed thread/provider/profile/epoch tuple; different accounts, threads or generations cannot alias |
| Private registry | Hub-owned `providers/accounts-v1/profiles.json`, mode 0600; profile/store UUIDs and identity fingerprint, no raw credentials |
| Provider stores | Private 0700 profile/attempt directories; fresh candidate for each login, verified promotion, obsolete/canceled-store cleanup |
| Login attempts | Transient hub/profile/attempt/CLI-login-ID binding, ten-minute expiry and bounded slots; excluded from durable event metadata and hub caches |

Claude children use `CLAUDE_CONFIG_DIR`; real `HOME` is preserved. Verification requires the exact `configDirectory` reported by Claude Code 2.1.268 or later and `authMethod: claude.ai`. Claude Console profiles use a different store and are not supported by this subscription-profile flow. Codex children use `CODEX_HOME`, file-backed CLI auth, and the OpenAI model provider. Inherited API keys, token selectors, cloud-routing overrides and alternate profile selectors are scrubbed per child. Codex diagnostic verbosity is restricted. Environment changes are never global. These directories separate stores under the same OS user; they are not an OS sandbox.

Captured thread mutations carry the account binding they were composed against. The server checks that binding before accepting work; a stale outbox/reconnect cannot send through a newly selected account. Global Settings/account-management requests have no conversation owner. View actions use the authoritative selected target. Restarted profiles are unchecked until provider verification; launch revalidates identity before creating the child. Identity replacement retires stale running ownership and requires explicit selection of the new generation. Concurrent independent threads may share one profile's provider store while retaining different native sessions; verification is serialized per profile.

Completed Git jobs report through typed internal messages, separate from client RPC and its account fences. Branch changes, Git notes, removal, merge observations and snooze results reconcile canonical metadata even for named threads. Worktree creation/fallback captures its provider and account binding: a stale completion records the filesystem result but cannot release queued model work under a different owner. Title and summary model callbacks retain their captured account checks.

## Catalogs and allowance

Both provider catalogs in the model picker are scoped to their saved profile and identity generation. A missing or stale named profile does not borrow the default account's catalog. Codex metadata uses `account/read`, `model/list` and `account/rateLimits/read`; the quota collector has a five-minute gate. Claude catalog discovery is an initialize-only control request, with no user/model prompt. Claude allowance is populated only from actual passive rate-limit windows received on the current account generation.

Used percentage, reset time and window duration are displayed only when the provider reports them. Missing values remain unknown; older readings become stale. Provider limit bucket IDs do not establish a per-model entitlement mapping. Profiles may share provider pools, and their allowances are never added together. Locally counted tokens/costs are not remaining subscription quota. No paid model probes, account upgrades or budget changes are part of qualification.

Primary contracts: [Codex app-server authentication](https://learn.chatgpt.com/docs/app-server#authentication), [Codex environment](https://learn.chatgpt.com/docs/environment-variables), [Claude authentication and multiple accounts](https://code.claude.com/docs/en/authentication#log-in-with-multiple-accounts), [Claude auth status CLI](https://code.claude.com/docs/en/cli-reference#auth-status). Exact pinned source/file-line links and the API-key versus subscription distinctions are retained in the research document.

## Qualification and integration

Evidence is retained under `build/multi-account/`: guard source/output clearances, exact source maps, normal server/web build receipts, executed /IO/hub/browser logs and desktop/390px screenshots. The fake provider programs never contact a provider or run inference. Test entry points are `test/accounts*_test`, `test/tools/accounts_io_test.cjs`, `accounts_hub_e2e.ts`, `accounts_metadata_e2e.ts`, `accounts_ui_e2e.ts` and the explicit-input frozen-native replay `accounts_native_replay.mjs`. Browser qualification needs the repository browser helper's Playwright dependency (or `BACKPLANE_PLAYWRIGHT_MODULE`) and a local Chromium executable. Build/test work is serialized through Backplane's named locks.

The shared server/client contract offers `accountProfiles: 1` only from updated web views. Existing `ios-v1`/`nativeSidebar: 1` markers do not grant account support. Unsupported named-thread reads retain bounded valid Screen/Out data with a visible error and no commands; provider mutations are refused before enqueue/spawn. The frozen released native bridge was replayed against an actual built-service refusal. Foundation-only actual Screen/Out decoding is qualified separately by the existing native owner, without a new app/archive/TestFlight distribution. The actual captured service draft is empty; a nonempty decoder sentinel is not a new service-level draft guarantee.
