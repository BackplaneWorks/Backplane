## Remaining cold-launch reliability work

Source review found that the automatic presentation-cache write restarts its 300 ms debounce on every accepted screen. A sustained stream of updates less than 300 ms apart can therefore postpone that write indefinitely unless an independent `keep()` or background flush occurs. This is a conditional scheduling risk, not an observed explanation for the measured launch times.

Fixed-window helper source `3c2347490e1476f7df3315e16f6f45efa25f3185` passes ten Foundation checks in work 704796, including sustained updates, latest-at-deadline, canceled late wake, subsequent window, actual temporary ScreenCache files, identity mismatch and retired saves. Initial work 704752 failed in its shell wrapper before compilation and is not a helper failure. The reviewed app binding reads current state through `keep()` at the first offer's deadline and cancels the window before retirement or clearing. Existing profile/link identity, save-generation barriers, background flush and cached-as-unready checks remain. The binding compiles in 6e1 and its three real-hub navigation/foreground sessions pass; this does not establish background durability or a causal latency benefit.

The 6e1 UI distinguishes a known conversation refresh from first opening and retains an owner-bound offline label alongside timeout/Retry. Explicit custom scrolling, zoom and highlight code reads Reduce Motion; runtime behavior remains unqualified. Targeted selected-tab text, section headings and row-age contrast changes follow same-result generic crops; they do not imply resolution of the whole Home audit.

## Explicit account-change isolation

Source review identified a privacy defect in the old pairing-retirement filter: hub-qualified snapshots were removed, but raw room and remote routes have no hub prefix and could survive replacement or removal of a pairing. The new conservative policy discards those ambiguous routes on explicit account-set changes and retires the specified hub’s qualified snapshots, drafts and navigation while preserving other qualified hubs. Ordinary network reconnects do not invoke this retirement.
