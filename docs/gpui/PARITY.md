## Rules for each status

- **done**: the code is present AND there is evidence it works: a test, a parity scenario, a results file or a screenshot, named in the evidence note. A feature only counts for a client when it works against the hub it is judged with.
- **partial**: code present without proof (no test, scenario or shot), or proof of only part of the row, or code that exists only on a lane branch that has not landed on `gpui`, or a row whose hub path is not yet at protocol parity (see the gate).
- **missing**: no code, a stub of 3 lines or less, or the request answers `unknown method`.
- **n/a**: the column truly does not apply (a desktop-only or phone-only feature, or a hub-internal row for a client).
- **Rust hub column** is derived: `missing` when none of the row's requests/tools/routes/providers is registered anywhere; `partial` when only some are, or all are registered but the row names no proof, or the only code is on a lane branch; `done` when every one is registered on `gpui` and the row names a proof. Rows without requests carry a hand-written hub status under the same rules. A client never makes a hub row better, and the hub row is not credited because Bend's presenter draws the screen.
- The iOS and Android apps run today's Bend client (`bridge.js`) inside native screens, so the code exists for most rows; their proof so far is on the JS hub (`build/gpui/shots/{ios,android}`, `build/gpui/results/{ios,android}`), none on the Rust hub. A phone cell is `done` only where a shot or result file shows that feature, otherwise `partial`.
