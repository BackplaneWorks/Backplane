# Updating and restarting a hub

A hub moves to a new build in one way only: its updater (`native/host/src/update/`) finds and stages a signed release, and the guard (`native/guard`, the `backplane` program) swaps to it, checks it, and goes back when it fails. The Bend hub's `deploy_main` / `deploy_restart` path (build origin/main in place, the `deploy.ship` and `deploy.wait` settings) is gone: old logs' `DeployAsked` and `DeployBuilt` events still fold, and set nothing (`state/fam.rs`).

Dev machines do not use this: `scripts/dev-build.sh` builds `native/host` and `native/gpui` and `scripts/dev-cut.sh` publishes them; `scripts/fresh.sh` sets `BACKPLANE_NO_UPDATE=1`.

## Installing: the guard from the first start

A release archive (`backplane-<tag>-<target>-native.tar.gz`; the `-native` keeps 0.14's updater, which takes any asset ending in `<platform>.tar.gz`, from picking it) holds `backplane-hub`, `backplane-gpui`, `backplane` (the guard), `assets/` and `COMMIT`; `release.yml` builds the guard for every target and fails the job when it is missing. `install.sh` (`deploy/install.sh.in`, filled in by `release.yml` with the version and each archive's sha256, published beside the archives) checks the archive and lays it out as the guard expects, under `BACKPLANE_PREFIX` (`~/.local/share/backplane`):

- `builds/<tag>/`: the unpacked release, made by one rename;
- `CURRENT`: the build that runs;
- `backplane`: the guard, copied out of the build, so an update never replaces the program running it; linked as `~/.local/bin/backplane`;
- `~/.local/bin/backplane-app`: the desktop app of `CURRENT`.

Nothing starts the hub directly. The desktop app finds this layout around itself (`launch::guarded_install`) and starts its home's hub with `backplane hub run --home <home> --port <port> --builds <prefix> --default`; a build tree with no such layout still starts `backplane-hub` beside it. With no desktop app (`BACKPLANE_NO_DESKTOP_APP=1`), or with `BACKPLANE_START=1`, the installer starts the guard itself for `BACKPLANE_HOME` on `BACKPLANE_PORT`. Run again while that home's guard runs, the installer asks it `backplane hub update <tag>`: the new build on probation.

## From 0.14

0.14 updates itself its own way (`src/server/update.bend` at v0.14.1): when the person presses Update it takes the first release asset ending in `<platform>.tar.gz` (on linux-x64 `linux-x64-cef.tar.gz`), checks it against the release's `SHA256SUMS`, unpacks it, runs `backplane-<platform>/install-release.sh <src> <prefix>` from it and re-execs `<prefix>/backplane-serve` with its own arguments. So every release also carries, for linux-x64, linux-arm64 and darwin-arm64, a 0.14-format archive and `SHA256SUMS` (`release.yml`, "the way from 0.14"), and the 0.15 archives are named `-native` so 0.14 never takes one. The 0.14-format archive holds the native archive, the signed manifest and `deploy/compat/`:

- `install-release.sh` checks the native archive against the manifest, lays it out as `builds/<tag>/` with `EXPECT` (the manifest's version and commit), copies 0.14's server to `backplane-serve.0.14` and its launcher to `backplane.0.14`, puts the guard at `<prefix>/backplane`, writes `NEXT` and replaces `backplane-serve` with the shim. Each file is written beside and renamed in; a failure leaves 0.14 as it was.
- The shim (`backplane-serve.sh`), on 0.14's re-exec, writes `builds/v0.14-legacy/backplane-hub` (0.14's server with 0.14's home and arguments) and starts the guard on **0.14's port**, so phones and machines paired to it, and a `tailscale serve` mapping, still reach it. The guard starts on 0.14, then is asked `backplane hub update <NEXT>`: 0.15 on probation, with the identity check against `EXPECT`. If 0.15 fails, the guard goes straight back to 0.14, so something always runs.
- 0.15 gets its own home (`~/.backplane/hub`; macOS `~/Library/Application Support/Backplane/hub`). The shim passes 0.14's home as `BACKPLANE_IMPORT_FROM`; 0.15's setup offers to bring its projects, threads, bots and paired devices across (nothing is written until the person confirms; `GET /import/0.14`, `/import/0.14/run`). Paired phones keep working once imported; linked machines are linked again in Settings, Devices. 0.14's home is only read.
- `backplane` with no arguments opens 0.15's desktop app, so 0.14's link and menu entry keep working.

0.14 on Windows never updated itself: install 0.15 from `backplane-<tag>-windows-x64-native.zip` by hand (docs/install.md).

## Who updates itself

A hub the guard runs from a builds folder (`BACKPLANE_BUILDS`: `builds/<tag>/`, `CURRENT`, `BAD`, `.pins/`), and a desktop app whose install has no guard running because its hub is on another machine. Otherwise the updater says so and does nothing:

| state | when |
|---|---|
| `package` | no `BACKPLANE_BUILDS`: a package install or a plain folder; its package manager updates it |
| `off` | `BACKPLANE_NO_UPDATE=1`, or a copy of a real log (`copy::on`) |
| `idle` / `checking` / `downloading` / `waiting` / `installing` / `failed` | a managed hub |
| the app's own row (below) | a desktop app in a guarded install (`builds/<tag>/`, `CURRENT`, the guard at `<prefix>/backplane`) whose `launch.json` or `hubs.json` points to a hub on another machine: no guard runs on this machine, so the app keeps its own build (see "A desktop app on another machine's hub") |

The feed is GitHub Releases (`run::FEED`); only the environment (`BACKPLANE_UPDATE_FEED`) can change it, never a setting, because any paired client can write settings. The channel is the setting `update.channel`: `stable` or `beta` (0.14's stored `nightly` reads as `beta`).

## What triggers an update

- The hourly check (`Hourly`, `svc::due`), on every managed hub.
- `update.check` from any client: desktop Settings > Network's Check now, either phone's Settings > Updates (`update.check` over data/1), or a linked machine over the link. It looks now and installs what it finds.
- `app.update`: the same, as an explicit wish to install.

Every client gets the same answer, `update.status` → `{current, version, channel, state, note, checked, line, canCheck}`, where `line` is the sentence to show (`present::settings::update_line`). The clients draw it and decide nothing. Phones set the channel with `update.channel {channel}` (docs/PHONE-DATA.md).

**A running turn always holds an install.** When something newer is found while any thread's turn is `running`, the state is `waiting` ("installs when running turns finish") and the install goes ahead at the next pass with no turn running. Whoever asked, from wherever, nothing cuts a turn.

## Finding and staging (`update/run.rs`, `update/rel.rs`)

In this order, and each step must pass before the next one starts:

1. Fetch the release list. A release counts only when it carries all three signed files (`manifest.json`, `.sig`, `.keyid`), which the release workflow uploads last. Drafts and tags in the guard's `BAD` are skipped, so a build that failed here is never offered again; the next higher tag is.
2. `rel::offer`: the newest tag on the channel that is newer than this hub's version. Tags have exactly the shape `vX.Y.Z`, `vX.Y.Z-beta.N` or `vX.Y.Z-nightly.YYYYMMDD.N`, because a tag becomes a folder name.
3. **Signature.** `manifest.json`'s bytes are checked against `manifest.json.sig` (ed25519), under the key `manifest.json.keyid` names, before they are parsed. One key is trusted: `native/host/src/update/release.pub` (PEM SPKI; the raw key is the DER's last 32 bytes) under the ID in `release.keyid` (`6c899f869be656d3`, the first 16 hex of SHA-256 over the raw key), compiled in. The signature is the raw 64 bytes over the exact manifest bytes. A key ID that does not match the key means the key is not trusted at all. There is no second key and no way to add one in a default or release build; the private key is the repo secret `BACKPLANE_RELEASE_KEY` (`update/README.md`).
4. The manifest names this machine's asset (`linux-x64`, `linux-arm64`, `darwin-arm64`, `windows-x64`) with its size and sha256 (2 GiB at most).
5. Fetch the archive into scratch beside `builds/`, check its size and sha256, then list it before writing anything (`run::members_ok`, `tar -tzf` and `tar -tvzf`, which must agree line for line). Only plain files and folders get through: no absolute path, no `..`, no symlink, no hard link, no device. Unpack with `--no-same-owner --no-same-permissions`, then check the tree again: there must be a runnable `backplane-hub`, and no link of either kind (a file with more than one link counts as a hard link).
6. Write `EXPECT` = `{"version","commit"}` from the verified manifest. This is written by the updater after the tree check, so the archive cannot choose what its build is held to.
7. One rename makes `builds/<tag>`, whole or not at all. Scratch is removed however the steps end.
8. Write `update/pending` (`<tag>`) and the guard request `guard/request` = `{action:"update", build:<tag>, from:"local"}` (beside it, then renamed). A request already waiting, perhaps a restart the person asked for, is refused, never replaced. While the update is pending and the guard has neither moved to it nor marked it bad, a restart of the old build reads it as "not yet" (`run::Outcome::Waiting`): the state stays `installing`, and the pending line stays.

The request is `from:"local"` because it is the hub's own. A phone or another machine asks the hub (`app.update`, `update.check`), never the guard's `hub.control update` directly: the guard refuses a remote switch to a build that has not yet run here with the control route, since going there could lock the asker out.

## Probation and the health check (guard)

The guard runs the new build on probation, with the build it left kept as the way back.

- It probes `GET /healthz`. A hub that is `starting` or still `folding` history is not yet proven; one that stops answering for `misses` probes in a row, or stalls during its start, is killed and counts as failed.
- **Identity.** On the first well probe the guard compares the hub's `version` and `commit` with `builds/<tag>/EXPECT`. They are the same values `/hello` reports (`{"backplane": version, "commit": ...}` in CBOR); `/healthz` carries them in JSON only to a caller with a credential the hub accepts (the guard sends the home token); being on loopback is not enough, because `tailscale serve` arrives on loopback. Commits match as a prefix of at least 7 characters (the manifest has the full SHA, the build the short one), and `unknown` never matches. A mismatch is a failure: "answered as v/c, expected v/c". It usually means the old hub still holds the port, or the archive held the wrong binary. With no `EXPECT` there is no comparison. The commit is compiled into the hub (`option_env!("BACKPLANE_COMMIT")`, set by `release.yml` and `scripts/dev-build.sh`); the runtime environment is only a fallback for other builds and the guard does not set it, so the comparison proves something.
- **Proven**: the identity matches, then the hub stays well for 60 s after its folds reach 0. Then the guard adds the build to `guard/good`, publishes it as `CURRENT` and pins it with up to two predecessors (`.pins/`), so pruning keeps them.

The guard takes one request at a time: a second one gets 409 unless the first is over 30 s old. The hub's own requests go through `guard::control(home, action, build, "local")`, which skips the remote limits.

## When and how it rolls back

- **During probation, automatically.** The first failure goes straight back to the previous build, with no retries (`plan::next_on`, `probation`). A failure is a crash or panic, a stalled start, missed health checks, or an identity mismatch. The guard writes the tag to `BAD` with the reason, sets checkpoints aside (never deletes them), starts the previous build, and records an incident.
- After the restart, the hub works out how its update ended (`run::outcome`): `Updated to <tag>.` (it then prunes old builds), or `failed` with "<tag> failed its health check, so this build stayed: <why>". Every client shows that line.
- **After probation**, a crash follows the normal ladder: the same build again 3 times within 10 minutes, then the newest good build, then safe mode, then rescue. Exit 75 (port or home lock held, disk full) and exit 78 (refused: a copy gate, a bad flag) are the machine's fault and never mark a build bad.
- **By hand**: `backplane hub rollback [--now]` at the machine, or `POST /hub/control {action:"rollback"}` from a phone or a linked machine with the hub's credential. Either marks the running build bad and goes to the newest good build that is not bad. From a remote client the target must have the control route, so the asker can still reach the hub afterwards. Remote requests are limited to 3 in 5 minutes, and a remote client can never stop the hub. `backplane hub use BUILD` takes a bad mark off and runs that build.
- **Rescue**: when nothing starts, the guard itself answers on the hub's port. `/healthz` returns 503 `down`, and `/hub/status` and `/hub/control` take the same credentials as the hub, so a phone can still restart or roll back.

## The test key (feature `e2e-trust`)

The update E2E (`test/update/`) needs releases it can sign, and it never signs one with the real key. A hub built with `cargo build --features e2e-trust` also trusts one public key (PEM) from the file `BACKPLANE_E2E_TRUST_KEY` names, and only for releases below `0.1.0` (`rel::E2E_CEILING`), so a leaked test release would offer nothing. The E2E makes a fresh keypair in its private home for each run and deletes it at the end; no private key is committed. Default and release builds have none of this code: the feature's code carries the string `backplane-e2e-trust-enabled`, and `release.yml` fails a build whose `backplane-hub` contains it. A unit test shows a default build refuses a manifest signed by such a key.

## A desktop app on another machine's hub

A desktop app set up to use a hub on another machine (`~/.config/backplane-gpui/launch.json`: `"home": ""`, `"url": "http://HOST:PORT"`, or a paired remote hub in `hubs.json`) starts no hub, so no guard runs on its machine. Nothing looked at the release feed and nothing moved `CURRENT`: such an install stayed on the build it was installed with, and Settings showed only the remote hub's update line, which said nothing about it. The app now keeps its own build, with the hub updater's trust rules and the guard's files, and moves to a new build only where no other app runs and only once that build has opened its window here.

**Who does what.**

- `backplane builds keep --builds <prefix> --running <tag> --channel <c>` (the guard, `native/guard/src/keep.rs`) finds, verifies and stages. It runs the hub's own `update::rel` and `update::run`, compiled into the guard by path as `scopeprobe.rs` already is, so this is the same code and not a copy: strict channel matching (nightly tracks only nightlies), HTTPS-pinned release downloads in production (`curl_url_ok`, `--proto =https`, `-q`, `--`), the signed manifest under the one compiled-in key, the tag's shape, `BAD`, the archive's size, sha256 and members, runnable `backplane-gpui` verified in scratch before rename, `EXPECT` (`{version, commit, sha256}`) checked on any existing tree, and one rename into `builds/<tag>/`. Then it writes `app-update/next` under `app-update/state.lock` and stops. It never starts or stops a hub, never touches a build that runs, and prunes under `state.lock` with the guard's rule (`run::prunable`, which also pins `app-update/` pointers). One runs at a time (`app-update/lock`). With a guard running on this prefix (`.guard.lock`, or legacy `.pins/<port>` answering `/healthz`) it says `guard` and does nothing, because that guard owns `CURRENT`.
- The app (`native/gpui/src/selfupdate.rs`, with the rules in `native/guard/src/appkeep.rs`, which both programs compile) does the rest. It runs only in a guarded install whose launch uses a hub on another machine: either `launch.json` has a `url` with no `--url`, `BACKPLANE_HOME`, or local hub this client was started on, or `hubs.json` points to a paired non-loopback remote hub (and switching hubs in-process updates this eligibility via `switch_hub`). It never runs under `$APPIMAGE`, `BACKPLANE_HUB_BIN`, `BACKPLANE_NO_UPDATE=1`, or special test/script flags. A package install has no `builds/` layout, so it never runs there either.
  - **At launch, before any window** (`appkeep::start`): every app of a prefix holds `<prefix>/clients.lock` shared while it runs. A launch that can hold it alone may move to another build; one that cannot stays where it is, so no build changes under a running app.
    - A staged build newer than this one, eligible for the active channel (or marked `app-update/manual`), not in `BAD` and present is tried. The launch writes `app-update/trial` (`{tag, from, at, pid, nonce}` under `state.lock`) and replaces itself with that build's app (`BACKPLANE_APP_TRIAL=<nonce>`; `exec` on Unix keeping `CFProcessPath` so `Backplane.app` stays the app macOS launched; spawned on Windows with its PID recorded before releasing `clients.lock`). `CURRENT` still names the old build.
    - A launch of the build a trial came from where that trial's PID is no longer alive means the trial never presented its window. That trial is marked `BAD` ("its app never opened its window") and this build runs. A launch while `trial.pid` is still alive stays without marking it bad, and a third build forgets the trial without blaming it (`CURRENT` moved by hand).
  - **First frame presented** (`appkeep::opened`): scheduled after the first frame draws and presents (`window.on_next_frame` -> `request_animation_frame` -> `app_opened`), verifying `nonce`, `CURRENT == from`, and `!BAD`. A trial is added to `app-update/good`, becomes `CURRENT` and clears `next` (leaving any newer `next` staged since the launch intact). The build `CURRENT` already names is recorded as good. Then this build's own guard runs `builds keep`, detached, and again every six hours while the app runs (recovering automatically if a helper exits early while `checking`/`downloading`).
- `CURRENT` only ever names a build whose app presented on this machine. The launchers (`deploy/mac/launcher.c`, `backplane-app` from install.sh, the Windows guard's `backplane` with no arguments, which the Start-menu entry runs) only read `CURRENT` and run its app, so none of them changed: the switch happens inside the app they start, and every launcher already installed keeps working. A new build that crashes before its window presents costs one launch: the next launch runs the old build again, marks the new one bad and opens.
- Pruning keeps `CURRENT`, the newest three good builds (a second app opened before a switch still runs the build `CURRENT` named then), the staged build, both sides of a trial, the running build and anything pinned.

**Why the guard stages and the app switches.** The guard gets the fetch-and-stage step because the trust rules already live in the hub's updater, and the guard can compile the same files with three small dependencies (`ed25519-compact` from the hub's vendor folder, `base64`, `hex`). The app stays free of the updater, and the step runs detached, so it finishes even if the window closes. The guard cannot do the switch, because nothing runs it at launch: the launchers run the app directly, and launchers already installed are never rewritten by an update. So the app judges and moves `CURRENT` itself, through `appkeep.rs`, which the guard compiles too. `store::Builds::mark_bad`/`publish` write `BAD` and `CURRENT` through it, so the format has one writer.

**Channel.** The hub's, so the app and the hub move to the same releases. The app asks the hub's `update.status` at each connection and hourly, and keeps its channel and version per hub in `app-update/hub.json` (`hubs.<key>`) for checks made before a connection (`selfupdate::hub_said`). A channel that changes starts a check at once (serialized cleanly via `CHECK_IN_FLIGHT`/`CHECK_AGAIN`, and a keeper seeing a channel change waits on `app-update/lock` to re-check rather than dropping it). An ineligible staged build from an earlier channel is cleared from `next` (unless `manual`). This device can choose its own instead (`local-settings.json`'s `app_channel`: empty follows the hub; `stable`, `beta` or `nightly` is this computer's alone), with the chips in its Settings row: "Same as the hub (nightly)", stable, beta, nightly. The feed comes only from the environment (`BACKPLANE_UPDATE_FEED`), never from a setting, and `BACKPLANE_NO_UPDATE=1` turns all of this off, as for the hub.

**Restart to update.** A build staged here is offered at once rather than at the next launch. The sidebar says "Backplane 0.16.1 is ready." with Restart to update, and the Network row has the same button. If another window of this install is still open (`clients.lock` contended), Restart stays open and asks you to close other Backplane windows first. When alone on Unix, it replaces the running process directly via `exec` (preserving macOS `Backplane.app`); on Windows it spawns the launchers' app (`CURRENT`) with `BACKPLANE_APP_AFTER=<pid>` and exits, which waits until that PID releases `clients.lock` and tries the staged build (promoting `CURRENT` once its window presents). The hub is not touched, so nothing running there stops.

**Versions apart.** The sidebar also says when this app and its hub run different versions (`selfupdate::skew`). "This app is 0.15.2; the hub runs 0.16.0." comes with Check now (this app looks again). "The hub runs 0.15.2, older than this app (0.16.0)." comes with Check the hub (`update.check` on the hub when `canCheck` is true, which installs what it finds when no turn runs). When a build is staged here, Restart to update comes first.

**What the person sees.** A desktop client connected to any hub shows its own version beside the hub's, which is labelled "Hub: Backplane …", on Settings > Network and Settings > About: the two can differ (and Settings notes when they differ with a warning tone). Where the app is updated by this computer's hub (its guard) or by its package, the Network row says that. Where it keeps its own build, the row reads "This Mac's app: 0.16.0" (or "This computer's app") with "Up to date, checked 14:05", "v0.16.1 is ready: used the next time Backplane opens", "Updated to v0.16.1", "v0.16.2 did not start, so this build stayed", or a localized check-failure message (`gpui.appupdate.err.*`; raw details stay in `status.json` and `keep.log`). The row offers Restart to update (when a build waits), Check now and the channel chips. The words come from `appkeep::line` over `app-update/status.json`. The hub's own Check now beside it checks this device too. Phones are unaffected.

**A hand install.** On Windows, unpacking a newer zip and choosing Install puts it in `builds/` and, when no guard runs and `CURRENT` names an older build, writes it as `app-update/next` + `manual` and launches a tracked trial so `CURRENT` promotes once its window presents; when a guard owns the prefix, it leaves `CURRENT` and `next` to the guard. On Linux and macOS, install.sh run again with no guard running writes `CURRENT` itself, and a pending trial is forgotten, not blamed.

Tests: `appkeep::` and `keep::` in the guard (`cargo test`, no network; the hub's `update::` tests run there too), `selfupdate::` in the client, and `test/update/app-e2e.sh GUARD GPUI` end to end. That test builds A, B and a broken C on a loopback signed feed, with the real client under a private Xvfb: A stages B and stays as it was, a second app leaves the build alone, the next launch runs B and makes it `CURRENT`, C dies at its start and is marked bad, and B keeps running.

## Checking an update from far away

The client that asked keeps polling `/hello` (never `/healthz`, which tells a caller without a credential nothing of the build). The update is done when it answers with the new version and commit. When it still answers with the old pair after the guard's boot and stable time, and `update.status` says `failed` with the tag, the update was rolled back. `/hub/status` (paired) shows the guard's view: build, commit, good, bad, last request and recent incidents.

Tests: `update::` (`cargo test`, no network), the guard's `plan` and `run` tests, and `test/guard/faults.sh` on a private home and port (`native/guard`). End to end: `test/update/feed.sh BIN_DIR` (a real guard and an `e2e-trust` hub against a signed feed on loopback: good, panic, die, mismatch, older, wrongkey, ceiling, healthz, and with PHONE the Android app's Check now, Restart hub and Roll back), and `test/update/clients.sh HUB CLIENT...` (a hub held on this desktop, backplane or the Mac, driven from the GPUI client on another machine or the Pixel), and `test/update/install-e2e.sh FIRST NEXT BROKEN` (three release dry runs: install.sh lays one out and starts the guard, the next updates it from a loopback feed, a broken one is rolled back).
